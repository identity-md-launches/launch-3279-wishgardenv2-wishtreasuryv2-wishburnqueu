# Dependency verification and activation blockers

The implementation uses the existing IMD contracts and their actual LayerZero V2 OFT v1 interfaces. Verified source/ABI records inspected for this revision:

- [Ethereum IMD / BridgedFP](https://sourcify.dev/server/v2/contract/1/0xd34a99bc0f67ae1bbd63c660e6d0b0dd03e263b7?fields=all): OFT `send`, `quoteSend`, no public ERC20 burn, 18 local / 6 shared decimals, caller debit without approval.
- [Base IMD / FrenPetToken](https://sourcify.dev/server/v2/contract/8453/0xFF0C532FDB8Cd566Ae169C1CB157ff2Bdc83E105?fields=all): inherits OpenZeppelin ERC20Burnable; `burn(amount)` invokes `_burn(msg.sender, amount)`.
- [Base official peer / FrenPetOFTAdapter](https://sourcify.dev/server/v2/contract/8453/0xab152db8aac047b6757ffcf495ffe88d7712690a?fields=all): underlying Base token, default OFTAdapter release and OFT compose format. The default adapter assumes lossless transfers and reports requested credit without its own recipient balance-delta check.

The official-peer address above was discovered from Ethereum IMD `peers(30184)`, not guessed. Reverify the reciprocal peer and underlying token at the time of setup. Typed subsets compile offline; upstream MIT ABI/codec snapshots and content hashes are supplied in `docs/bridge/`. The actual deployed token/adapter runtimes are archived as test data and executed locally with fresh storage. No new production adapter or token is introduced.

Historical Ethereum/NFT evidence from the pinned project remains at `docs/evidence/ethereum-dependencies.json`; it is dated historical evidence, not proof of this replacement's activation. The revised read-only observer is `scripts/check-dependencies.py`. A successful current observation is stored separately as `docs/evidence/bridge-observations.json`. Its block numbers/hashes and raw calls distinguish it from a mocked test. Neither file is a complete activation attestation.

The successful revision observations at Ethereum block **26426738** and Base block **58157371** (exact hashes in the JSON) returned endpoint `0x1a44076050125825900e736c501f859c50fe728c` on both chains, with EIDs **30101** (Ethereum) and **30184** (Base). Their runtimes differ by chain immutables. The Base peer is `0xab152db8aac047b6757ffcf495ffe88d7712690a`. These observed values are deliberately not supplied as a fabricated receiver deployment or as automatic activation defaults.

## Required owner review before freezing and activation

- Check confirmed Ethereum source commit, constructor arguments, owner, reciprocal garden reference and deployed bytecode. Verify Ethereum contracts are disabled initially. Review Base source and deploy it separately with the **confirmed** treasury address; verify every immutable against receipt and runtime.
- Verify Ethereum token source/code/18 decimals, actual `endpoint`, endpoint EID, `peers(baseEid)`, `token`, `approvalRequired == false`, OFT interface/version, shared decimals and rate. Verify Base adapter source/code, underlying token, endpoint/EID, reciprocal Ethereum token peer and the same encoding/decimal assumptions. Do not substitute chain IDs for EIDs.
- Inspect existing token/adapter governance, message inspector, enforced SEND_AND_CALL options, send/receive libraries, required/optional DVNs and thresholds, confirmations, executor and native gas caps. Review both the OFT path and the **new receiver-to-treasury default acknowledgement path**. These new apps do not expose message-library/delegate administration. Inappropriate defaults are a blocker, not an invitation to guess configuration.
- Verify Base adapter reserve liquidity. Simulate a positive credit to the exact receiver and its positive public burn with truthful before/after balances and totalSupply. Check Base token transfer/trading/AMM/fee/max-transaction/blacklist flags applicable to the adapter and receiver. Live read on 2026-11-16 (pinned Base block `0x378042e`, raw results in `docs/evidence/bridge-observations.json`): `limitsInEffect` true, `tradingActive` true, `maxWallet` 3e42 (above total supply), `maxTransactionAmount` 5e23, adapter neither blacklisted nor fee-excluded; the token owner can change all of these. The readiness probe now refuses on `isBlacklisted(receiver|adapter)`, on inactive trading under limits unless adapter or receiver is fee-excluded, and on a `maxWallet` that cannot take one frozen `maxBatch` (after burning anything the receiver already holds), but it reads those flags only at that moment and the zero-burn probe alone still does not prove positive credit.
- Verify the receiver derivation: `treasury.receiverCreationCodeHash()` equals `keccak256` of the compiled `BaseBurnReceiver` creation bytecode in `base/package/BaseBurnReceiver.deployment.json`; `treasury.predictReceiver(baseEndpoint, baseOFT, acknowledgementGas, maxBatch, salt)` equals `DeployBaseReceiver.predict(...)`; the deterministic deployer `0x4e59b44847b379578588920cA78FbF26c0B4956C` has code hash `0x2fa86add0aed31f33a762c9d88e807c475bd51d0f52bd0955754b2608f7e4989` on Base; and the live endpoints report `eid()` 30101 (Ethereum) and 30184 (Base), the constants the treasury pins. The owner's remaining freeze inputs (Base endpoint, adapter, gas, maximum batch, salt) cannot redirect funds: a wrong value produces a receiver that fails its own checks and never signals readiness, which blocks activation. Never deduct token fees from the 30% or accept a reduced credit. No real-fund test purchases are authorized or required by these scripts.
- Verify source `SendParam` encoding, original-caller compose binding, exact type-3 options (receive + compose index 0), gas with margin, native fee quoting, refunds, uint64 shared amount bound and destination credit. Simulate failure/low gas and retry behavior with final addresses. Add separately funded native gas for the return acknowledgement. No token allowance is needed on Ethereum and the receiver must approve nobody.
- Verify final receiver's Base `IMDBurned` checks and Ethereum return authentication, source EIDs/peers, `allowInitializePath`, unordered delivery and duplicate handling. Run/read the readiness handshake through the real endpoints before activation. A browser assertion or owner evidence hash cannot substitute for an authenticated burn message.
- Preserve actual evidence bytes and hash before `freezeBridge`. The contract only stores a commitment to owner-reviewed evidence; it cannot independently inspect remote code/security settings. Freeze is one-time. Confirm the recorded hash/settings and all earlier evidence before `activatePurchases`.

## Open status and trust limits

The source assignment does not have confirmed replacement Ethereum deployment addresses, source publication/commit receipt, a deployed Base receiver, positive final-address bridge-credit simulation, or approved DVN/default-route evidence. Those are explicit service/owner setup dependencies. Ethereum deployment is still useful and required **disabled**; none of these gaps is filled with a fake address, signer or a lock-as-burn fallback.

Existing bridge/token administrators may change peers/options/fees/transfer restrictions; default protocol libraries/DVNs can change outside this application's control. Local peer/runtime validation catches some changes; remote settings and availability still require monitoring. In-flight failures can remain in transit indefinitely. The application's lack of rescue is intentional custody restriction and creates a stranded-funds risk after an irreparable external dependency failure.

Legacy free-claim activation is the legacy owner's separate decision. This revision cannot enable, reset or migrate that ledger. All legacy sink balances remain locked without any claim that their totalSupply was reduced.
